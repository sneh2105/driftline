## 2026-11-06 21:21 · feat/auto-build · pending
**Change:** Added request body size capping and rate limiting on the ingest endpoints. A new `BodySizeLimitMiddleware` (server/app.py) rejects any request over 1MB with 413 -- checked up front via `Content-Length` and re-checked against actual bytes received as they stream in, so a chunked request that omits or lies about `Content-Length` is still caught. A new `rate_limit_ingest` dependency (server/app.py) applies a 300-requests-per-60s fixed-window counter per project to `POST /v1/approvals` and `POST /v1/approvals/batch`, returning 429 with a `Retry-After` header once exceeded; a batch request counts as one request regardless of how many events it carries.
**Why:** First unchecked TASKS.md item ("Rate limit ingest endpoints and cap request body at 1MB; document in SPEC.md") -- no QA xfail/BUG-n findings exist yet (tests/qa/ has only docs, no test files) and the full suite was green before this change. Went with an in-memory fixed-window counter and a raw ASGI middleware rather than pulling in a dependency (e.g. slowapi, redis) because the server is a single-process SQLite app for this stage (v0) and the SDK-must-be-stdlib-only rule signals the project wants to stay light on dependencies generally; a pure ASGI middleware also lets the body cap apply before any request parsing happens, which a FastAPI dependency can't do. The counter resets on process restart and doesn't span multiple processes, which is an accepted limitation for now and is called out in SPEC.md.
**Files:** server/app.py, tests/test_driftline.py, SPEC.md, TASKS.md
**Verified:** `pytest tests -q` -> 22 passed (added `test_oversized_body_rejected`, `test_body_under_cap_is_fine`, `test_ingest_rate_limited`, `test_rate_limit_is_per_project`). No web/ changes, so `npm run build` was not required.
**Notes/risk:** The 300 req/60s default is a judgment call for v0 with no production traffic data behind it; a human should sanity-check it against expected real-world ingest volume before this goes live. The in-memory counter won't work correctly if the server is ever run with multiple worker processes -- fine today (single process), but worth revisiting if that changes.
